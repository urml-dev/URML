# URML and IEC 61508

[IEC 61508](https://webstore.iec.ch/en/publication/5515) (Functional safety of electrical/electronic/programmable electronic safety-related systems) is the basic functional-safety standard. Sector standards build on it: IEC 62061 for machinery is one. A robot outside the machinery standards is designed to IEC 61508 directly, and so are many of the safety components robots are built from: safety controllers, drives with a safe torque off, safety-rated scanners.

This page says where URML stands under IEC 61508: outside the safety-related system, claiming nothing. The rest of the page explains what that means for an integrator who uses URML on a robot that has IEC 61508 safety functions.

It quotes nothing from the standard. IEC 61508 is copyrighted; read the requirements in a licensed copy.

## URML is not a safety-related system

URML was not developed to IEC 61508-3, the part on software. It has no systematic capability, no SIL, and no safety manual of the kind a compliant item ships with. The validator is not safety-rated, a refusal is not a safety function, and nothing in URML counts toward a safety integrity level. A URML runtime sends commands to a robot whose own safety-related control must keep it safe whatever URML sends.

URML still has a job. It runs above the safety system and refuses programs that break the site's limits before they move anything. That is a useful filter, and an integrator can show it in a risk assessment as a measure outside the safety functions. It cannot take a safety function's place.

## What URML offers instead

The rulebook template [`examples/rulebooks/functional-safety-template.yaml`](../../examples/rulebooks/functional-safety-template.yaml) accepts IEC 61508 levels (`SIL1` to `SIL4`) alongside ISO 13849 performance levels and IEC 62061 SILs. It refuses programs until the operator has declared, in a deployment rulebook, the level each safety function reached and the reference of the validation record. URML checks that the declaration exists and is high enough. It does not check that the declaration is true.

## Running on shared hardware

The simplest design keeps URML on a computer of its own, separate from any safety-related software. If URML does share hardware with safety-related software, IEC 61508 requires the integrator to show that the non-safety software cannot interfere with the safety software, or else to treat all of it as safety-related. URML supports neither argument with evidence of its own. The template lists this as the obligation `urml_cannot_interfere`.

## If URML is used as a tool

IEC 61508 sorts the software tools used to build a safety-related system into three classes, by what a tool fault could do. In our words:

- **T1**: the tool produces nothing that ends up in the executable code (an editor, for example).
- **T2**: the tool tests or verifies the design or the code; a fault could hide a defect but could not put one in.
- **T3**: the tool produces something that ends up, directly or indirectly, in the executable code (a compiler, for example).

URML is not meant to be a tool for developing safety-related software, and we advise against using it as one. If an integrator does use the URML validator to check something a safety case relies on, it would be a T2 tool, and the standard then asks for evidence about the tool that URML does not supply: no tool qualification, no record of use in safety-related projects. The translator and the LLM bridge produce URML programs, and a URML program must never be part of a safety function, so the T3 question should not arise. If it does, the design is wrong, not the classification.

## Edition 3

IEC 61508 edition 3 is at the final draft stage for all seven parts, forecast for publication in 2027. Public summaries of the drafts report changes to the requirements on software off-line support tools in part 3. When edition 3 is published, this page and the template's cites will be checked against it.
