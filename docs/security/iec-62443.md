# URML and IEC 62443

[IEC 62443](https://webstore.iec.ch/en/publication/7033) (ISA/IEC 62443, Security for industrial automation and control systems) is the series of standards for the cybersecurity of industrial control systems. It splits a site into zones joined by conduits, gives each zone a target security level (SL 1 to 4) from a security risk assessment, and sets requirements for asset owners, integrators and product makers. Robot cells and fleets are part of such systems, so a site that works to IEC 62443 will ask where URML fits.

This page says where URML stands: URML is software inside a zone, it is not a security control, and it claims no security level. It quotes nothing from the standard; read the requirements in a licensed copy.

## What URML is under IEC 62443

The URML validator and a URML runtime are software on a host (a PC, an edge computer, a robot's onboard computer) that sends commands to a robot controller, a fleet manager or a broker. That host sits in a zone, and its link to the robot is a conduit. Both belong in the site's zone and conduit model.

URML was not developed under IEC 62443-4-1 (secure product development lifecycle), has no IEC 62443-4-2 component assessment, holds no ISASecure or other certification, and claims no security level capability. A site counts URML as software whose risk it assesses, not as a control that raises a zone's level.

## What URML contributes, requirement by requirement

IEC 62443-3-3 groups its system requirements under seven foundational requirements. For each, this is what URML does and does not do, in our words.

| Foundational requirement | What URML contributes | What it does not do |
|---|---|---|
| FR 1, identification and authentication control | The VDA 5050 and ISO 21423 runtimes authenticate to their broker, with a username and password or a client certificate. | URML does not identify or authenticate who submits a program. The host and the network must. |
| FR 2, use control | The validator refuses any program that breaks the robot's manifest, the site's envelope, the compliance policy or the rulebooks, before it reaches the robot. The MCP server lets the operator pin the manifest, envelope and rulebooks so an agent cannot replace them. | It restricts what a program may do, not who may send one. |
| FR 3, system integrity | Signed evidence reports can be verified offline (`urml evidence verify`). The validator runs offline and loads only the files it is given. | It does not check the integrity of the host, its packages or the robot's firmware. |
| FR 4, data confidentiality | The VDA 5050 and ISO 21423 runtimes connect to their broker over TLS 1.2 or newer when `broker_tls` is set, always verifying the broker's certificate and host name. Evidence reports can be redacted before they leave the site (`--redact`). | TLS is opt-in: without `broker_tls` the MQTT runtimes send in clear text, with a warning when the broker is not on the same machine. Other runtimes rely on their substrate's transport. |
| FR 5, restricted data flow | Reference runtimes need no cloud service and send no telemetry. | Network segmentation is the site's. |
| FR 6, timely response to events | Validation records (`--evidence-log`) log every accepted and refused program with digests of its inputs, for the site's security event logs. | URML detects no intrusion and raises no alarm. |
| FR 7, resource availability | Validation fails closed: a program that cannot be checked does not run. | URML gives no availability guarantee and no protection against denial of service. |

## Known gaps

- **Transport security is opt-in in the MQTT runtimes.** `urml-vda5050-runtime` and `urml-iso21423-runtime` support TLS, broker credentials and client certificates (`broker_tls`, `broker_username`, `broker_password_env`), but a config without them connects in clear text. Set them for any broker that is not on the URML host, or protect the conduit with the network.
- **No authentication of program sources.** Anyone who can run `urml` on the host, or reach a service that calls it, can submit programs. Control that with the host's accounts and the network.
- **Natural language and model output are untrusted input.** The LLM bridge's output reaches the robot only through the validator, which is the point of URML, but a prompt can still ask for anything the rules allow. Keep the rules tight.

## What URML offers instead

The rulebook template [`examples/rulebooks/cybersecurity-template.yaml`](../../examples/rulebooks/cybersecurity-template.yaml) refuses programs until the site operator has declared the security level achieved by the zone that holds the robot controller and by the zone that holds the URML host, both meeting their targets, and the references of the zone and conduit model and of the security risk assessment. Its obligations list what the system around URML must cover: authenticated, protected conduits; controlled program sources; patching; logging. URML checks that the declarations exist and that the levels are high enough. It does not check that they are true.

An [evidence report](../../examples/evidence-report/) of a deployment that loads the template lists those declarations and obligations under IEC 62443, next to everything else URML checks.
